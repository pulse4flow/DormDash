# ทีมและความพร้อมสำหรับ DormDash MVP

สถานะ: เตรียมงาน ยังไม่เริ่มพัฒนาฟังก์ชันใหม่  
อ้างอิงขอบเขต: [simple-resident-mvp-plan.md](./simple-resident-mvp-plan.md)

## เป้าหมายร่วม

สร้างระบบจัดการที่พักขนาดเล็กสำหรับ **เจ้าของและพนักงาน** หนึ่งแห่ง ให้ทำงานตั้งแต่บันทึกการจองจนเช็กเอาต์และเตรียมห้องรอบถัดไปได้ครบ แอปปัจจุบันเป็นเดโมสำหรับผู้พักหอ; โมเดลห้อง การจอง ผู้เข้าพัก และสิทธิ์พนักงานยังไม่ได้สร้าง

## ทีมและความรับผิดชอบ

| บทบาท | รับผิดชอบ | ส่งมอบก่อนเริ่มเขียนโค้ด |
| --- | --- | --- |
| Project lead | ตัดสินลำดับงาน ประสานข้อสรุปกับเจ้าของโปรเจกต์ คุมขอบเขต | ขอบเขต MVP และรายการตัดสินใจที่บันทึกแล้ว |
| Product/UX | สัมภาษณ์ผู้ประกอบการ ออกแบบงานรายวันและหน้าจอ | แผนผังขั้นตอนใช้งาน หน้าจอหลัก และเกณฑ์ยอมรับที่ผู้ใช้เข้าใจได้ |
| Architecture/Data | ออกแบบโมเดล สิทธิ์ สถานะ และกฎการจอง | แผน schema/API และกฎเปลี่ยนสถานะ |
| Implementation | ทำงานตามลำดับชิ้นเล็กที่ทดสอบได้ | โมดูลข้อมูลหลัก, API, UI และ migration ตามขอบเขต |
| QA/Release | ตรวจกรณีปกติ กรณีผิดพลาด และการใช้งานบนมือถือ | ชุดทดสอบและผลการทดลองครบหนึ่งรอบ |

บทบาทเหล่านี้เป็นความรับผิดชอบของทีม AI ในงานนี้ ไม่ได้หมายถึงการตั้งระบบหรือพนักงานถาวรเพิ่ม

## ลำดับส่งมอบ

1. **ยืนยันการใช้งานจริง:** คุยกับผู้ประกอบการ 3–5 ราย; ตัดสินขั้นตอนจอง เช็กอิน เช็กเอาต์ และงานแม่บ้าน
2. **กำหนดสัญญาของระบบ:** หน้าจอหลัก สิทธิ์แต่ละบทบาท สถานะห้อง/การจอง/งาน และเกณฑ์ยอมรับ
3. **วางฐานข้อมูลและสิทธิ์:** `Property`, `Room`, `Guest`, `Reservation`, `Stay`, `WorkOrder` และสมาชิกทีม; ข้อมูลใหม่ทุกชุดผูกกับที่พัก
4. **สร้างวงจรหลัก:** ตั้งค่าห้อง → จองแบบบันทึกเอง → เช็กอิน → เช็กเอาต์ → งานแม่บ้าน → ห้องพร้อม; เพิ่มงานซ่อมในคิวเดียวกันโดยแยกประเภท
5. **ทำหน้า “วันนี้”:** แสดงผู้เข้า–ออก ห้องพร้อม/ไม่พร้อม และงานค้างจากข้อมูลจริง
6. **ทดลองหนึ่งแห่ง:** เดินขั้นตอนครบหนึ่งรอบบนคอมพิวเตอร์และมือถือ แล้วเก็บปัญหาที่พบ

## ข้อตกลงทางเทคนิคเบื้องต้น

- ใช้ Next.js, TypeScript, Prisma และ PostgreSQL ตามฐานโค้ดปัจจุบัน
- ใช้ช่วงวันที่จองแบบ `[วันเข้า, วันออก)` ตามเขตเวลาของที่พัก; การจองที่ยังมีผลต้องไม่ทับกัน แม้มีคำขอพร้อมกัน
- แยกสถานะการเข้าพัก ความสะอาด และการปิดห้องซ่อม เพื่อคำนวณว่าห้องพร้อมรับแขกหรือไม่
- ตรวจสิทธิ์และขอบเขตที่พักบนเซิร์ฟเวอร์ทุกครั้งที่อ่านหรือแก้ข้อมูลผู้เข้าพัก/การจอง
- คงข้อมูลเดโมแจ้งซ่อมเดิมแยกจาก `WorkOrder` ใหม่จนกว่าจะมีแผนย้ายข้อมูลชัดเจน

## เกณฑ์ตรวจรับ MVP

- เจ้าของสร้างที่พักหนึ่งแห่ง ห้อง และบัญชีพนักงานพร้อมสิทธิ์ได้
- พนักงานเพิ่ม แก้ และยกเลิกการจองได้; ระบบปฏิเสธการจองห้องทับ
- หน้า “วันนี้” แสดงข้อมูลเข้า–ออก สถานะห้อง และงานค้างตรงตามวันที่เลือก
- เช็กเอาต์ทำให้ห้องต้องเตรียม; พนักงานปิดงานแม่บ้านแล้วห้องจึงพร้อมอีกครั้ง
- งานซ่อมมีผู้รับผิดชอบและสถานะ; ห้องที่ปิดซ่อมไม่ถูกแสดงว่าพร้อม
- ผู้ใช้เข้าถึงเฉพาะข้อมูลที่บทบาทและที่พักของตนอนุญาต
- ผ่านการทดลองตั้งแต่จองจนเช็กเอาต์บนหน้าจอมือถือหนึ่งรอบ

## งานเตรียมฐานโค้ดก่อนพัฒนา

- แก้ README และ `.env.example` ให้ตรงกับ PostgreSQL
- ทำคำสั่ง lint ให้รันโดยไม่ต้องตอบคำถาม และเพิ่มชุดทดสอบ/CI สำหรับวงจรหลัก
- แยกงานเดโมปัจจุบันกับงาน MVP ใหม่ในรายการงานและคอมมิต

## ประเด็นที่ต้องตัดสินจากการสัมภาษณ์

1. รับจองเป็นห้องที่ระบุทันทีหรือรับตามประเภทห้องก่อน? มี walk-in หรือไม่?
2. เมื่อยกเลิก ไม่มาเข้าพัก หรือออกช้า พนักงานทำขั้นตอนใด?
3. ใครเป็นผู้ยืนยันว่าห้องสะอาดและพร้อม? งานซ่อมแบบใดต้องปิดรับจอง?
4. บทบาทใดเห็นหรือแก้ข้อมูลติดต่อผู้เข้าพักได้ และเก็บข้อมูลไว้นานเท่าใด?
5. เดโมสำหรับผู้พักหอเดิมจะอยู่ร่วมกับระบบใหม่หรือแยกออกภายหลัง?

เมื่อได้คำตอบ ให้ Product/UX ปรับขั้นตอนและเกณฑ์ยอมรับก่อน Architecture/Data สรุป schema จากนั้น Implementation จึงเริ่มงานตามลำดับข้างต้น
